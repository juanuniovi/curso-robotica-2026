Ingeniería Robótica con MBSE

4º curso, Grado en Ingeniería Electrónica y Automática. 14 semanas.

Objeto · Metodología · Fases · Roles · Evaluación · Repositorio · Recursos

Objeto del curso

El curso aplica la ingeniería de sistemas basada en modelos (MBSE) a la elaboración de la oferta técnica de un vehículo terrestre no tripulado (UGV). El punto de partida es el pliego de una licitación pública real, con más de 80 requisitos, que se trabaja sin modificar.

Se recorre la rama descendente del ciclo en V: análisis de la necesidad, concepto de operaciones, requisitos, estudio de conceptos, arquitectura y plan de verificación e integración. El resultado final es una oferta técnica; no se construye ni se verifica el sistema completo.

Las evidencias de viabilidad que sostienen la oferta se obtienen de modelos de simulación y de un banco de pruebas con actuadores de laboratorio. El banco actúa como gemelo digital mínimo que contrasta la simulación con medidas reales; no es una réplica del vehículo.

Metodología: MBSE

La ingeniería de sistemas basada en modelos (MBSE, Model-Based Systems Engineering) es la aplicación formalizada del modelado a los requisitos, el diseño, el análisis y la verificación de un sistema, desde el diseño conceptual hasta el final de su ciclo de vida (definición de INCOSE).

En la ingeniería de sistemas basada en documentos, la información del sistema se reparte en documentos redactados por separado y la coherencia entre ellos se mantiene a mano. En MBSE la referencia es un único modelo del sistema: requisitos, funciones, estructura, interfaces y relaciones de trazabilidad son elementos de ese modelo. Diagramas, tablas y documentos son vistas del modelo, y un cambio en él se refleja en todas ellas.

El modelo se expresa en SysML (Systems Modeling Language). Cada fase del curso amplía el mismo modelo; la oferta técnica final es una vista de él.

Fases

Las fases se publican a medida que se alcanzan.

  1. Análisis de la Necesidad. Objetivo de esta fase: identificar a partir del pliego la necesidad, el problema y las partes interesadas, y modelar el contexto del sistema.
  2. CONOPS — Concepto de Operaciones. Objetivo de esta fase: modelar el uso del sistema: modos de operación, misiones principales y un escenario operacional de referencia.
  3. Requisitos de las Partes Interesadas. Objetivo de esta fase: formalizar en el modelo requisitos verificables y trazables al pliego, clasificados por subsistema y por verificabilidad mediante simulación.
  4. Estudio de Conceptos y Selección. Objetivo de esta fase: definir alternativas de solución y seleccionar una mediante una matriz de decisión ponderada, con cada criterio trazado a requisitos.
  5. Arquitectura SysML: BDD e IBD de primer nivel. Objetivo de esta fase: derivar los requisitos de sistema y modelar bloques, propiedades, interfaces y conexiones de primer nivel, trazados a requisitos. Se cierra con la línea base v1.0 del modelo.
  6. Plan de Verificación e Integración. Pendiente. Objetivo de esta fase: asignar a cada requisito su método de verificación y definir el esquema de integración entre subsistemas.
  7. Optimización y cierre. Pendiente. Objetivo de esta fase: completar el modelo con el plan de gestión (EDT, cronograma, presupuesto) y obtener de él la oferta técnica.

Roles

El grupo, de 4 o 5 estudiantes, forma un único equipo. El trabajo se reparte en cuatro roles, definidos por el tipo de evidencia que producen y no por subsistemas del vehículo. Los roles rotan a lo largo del curso por acuerdo del equipo. El rol de Sistemas coordina y es el interlocutor con el cliente, que es el profesor.

Sistemas (IS)
Requisitos, trazabilidad, arquitectura y estructura de la oferta. Herramientas: herramienta de modelado SysML, Requirements Toolbox.
Simulación (SIM)
Modelos físicos: eléctrico, transmisión, multicuerpo. Evidencia por simulación. Herramientas: MATLAB, simulador físico, Simulink Test.
Taller (TAL)
Banco de pruebas de laboratorio. Evidencia física (medidas reales). Herramientas: software de configuración y SDK del actuador.
Software (SW)
Adquisición de datos del banco e integración hardware–modelo. Herramientas: SDK del actuador en Python; ROS 2 opcional.

Evaluación

  • 50 % grupal: coherencia de la cadena pliego → arquitectura → simulación → evidencia.
  • 50 % individual: trabajo en los roles desempeñados y defensa individual en la revisión final (CDR).

Criterios:

Trazabilidad
Todo valor numérico debe citar el identificador del requisito del pliego que lo justifica. Cada valor sin referencia baja un nivel en la rúbrica. Se aplica desde la Fase 1.
Evidencia
Al menos el 80 % de los requisitos clasificados como verificables por simulación debe tener evidencia de viabilidad documentada, obtenida por simulación o en el banco de pruebas.
Revisión final (CDR)
La presentación muestra la cadena completa pliego → arquitectura → simulación → evidencia. Se valora más la coherencia entre niveles que la profundidad en uno solo.
Revisión cruzada
En una revisión intermedia (PDR) y en la CDR, cada rol somete su trabajo a la crítica del resto del equipo y lo contrasta con el modelo de referencia del profesor. Se evalúa también la calidad de las objeciones formuladas.

Acceso

Crea una cuenta en GitHub y envía tu nombre de usuario al profesor. Recibirás una invitación por correo al repositorio; acéptala.

Clonar (una vez)

En GitHub Desktop: File → Clone repository. Desde la línea de comandos:

git clone https://github.com/juanuniovi/curso-robotica-2026

Guía detallada: GitHub Desktop.

Ramas

  • En cada fase, cada rol trabaja en la rama rol/fase-XX, con rol = is, sim, tal o sw, creada a partir de master actualizado.
  • Cada rol modifica solo sus propias carpetas.
  • Al final de cada sesión: commit y push de la rama, aunque la tarea no esté terminada.
  • Al cerrar la fase se abre un pull request a master. Lo revisa e integra quien tenga el rol de Sistemas.
git checkout master && git pull
git checkout -b sw/fase-03
git commit -m "feat(sw): adquisición SDK + log de corriente"
git push origin sw/fase-03

Commits

  • Un commit corresponde a una unidad de trabajo; no se mezclan tareas distintas.
  • Formato del mensaje: tipo(rol): descripción, en presente, con el ID de requisito cuando proceda.
  • Tipos: feat añadir, fix corregir, docs notas y tablas, refactor reorganizar.
  • Si aparece un conflicto al hacer pull o en el pull request, se avisa al profesor antes de resolverlo.

Correcto: fix(sim): corrijo unidades del puerto PotenciaElectrica
Incorrecto: cambios, actualizado.
